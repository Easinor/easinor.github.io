01A question about the past

An attack on a cloud service is discovered on Friday. The logs say it began on Tuesday at 3:14 am. The security team has a numeric fingerprint of how the attacker’s session behaved, and wants the sessions that looked most like it. Not among all sessions ever recorded: among the sessions that were open at that moment. (The system maps that moment to a position in its update log; from here on, “time” means that position.)

This is a nearest neighbor search with a time machine attached. The same need shows up when auditing an AI system that answers from a changing document collection: to understand an old answer, you search the collection as it existed back then.

An ordinary vector index (the data structure built in advance so that searches are fast) knows one state of the data: now. This post explains FlashbackANN, our index for the question “who were the nearest neighbors of \(q\) at a given past moment?” Its main contribution is on the construction side: it is built in parallel batches, where the earlier index for this problem replays history one update at a time.

The whole idea in three sentences

A point that is missing from an index cannot be searched for. A point that is there but should not be can be filtered out. So process updates in batches, and freeze the index after each batch’s insertions and before that batch’s deletions.

The rest of the post unpacks those three sentences. All numbers come from the current draft of our paper.

02Vector search in three minutes

Modern systems turn documents, images or user sessions into vectors (also called embeddings): lists of a few hundred numbers, arranged so that similar items land close to each other. “Find similar items” then becomes nearest neighbor search: given a query vector \(q\), find the \(k\) stored vectors closest to it.

Comparing \(q\) with every stored vector is exact but too slow for large collections. Real systems use approximate nearest neighbor search (ANNS): they accept missing a few of the true neighbors in exchange for a large speedup. Two numbers describe how well that goes:

  • Recall is the fraction of the true \(k\) nearest neighbors that the index returned. Recall 0.99 with \(k = 10\) means that, on average, 9.9 of the 10 returned points are correct.
  • Throughput is the number of queries answered per second (QPS).

The most popular kind of ANNS index is a proximity graph. Every vector is a vertex. When a vector is inserted, it is linked to a few vectors near it (at most 32 in our experiments). A query walks this graph with a beam search:

  1. Start at a fixed entry point and keep a list of the best candidates found so far. The list has room for \(L\) candidates; \(L\) is called the beam width.
  2. Take the closest candidate that has not been expanded yet, look at its neighbors, and add them to the list.
  3. Keep only the \(L\) closest. Stop when everything on the list has been expanded, and return the \(k\) closest.

A larger \(L\) explores more of the graph, which is slower and more accurate. That is the knob behind every recall-versus-throughput curve.

One observation from this picture matters for everything that follows. The graph is not the data. It is a navigation aid. Many different graphs over the same points are valid indexes. Some navigate better than others, but none of them is the correct one, so an index is free to build whichever is convenient.

03Now add time

In the time-travel version of the problem, the data is a stream of updates: vectors are inserted, and later they expire. A timestamp \(ts\) is the position of an update in that stream (operation 0, operation 1, …).

Each vector has a lifespan \([s, e)\): it is inserted by operation \(s\) and removed by operation \(e\). It is alive at \(ts\) when \(s \le ts < e\). A time-travel query is a pair \((q, ts)\) and asks for the approximate \(k\) nearest neighbors of \(q\) among the points alive at \(ts\). Recall is measured against the true nearest neighbors among those alive points.

One detail shapes the whole problem: when a vector is inserted, nobody knows when it will expire. Its lifespan is complete only after the fact.

Four existing approaches

  • Post-filter. Build one graph over every point ever inserted, search it without regard to time, then keep the results that were alive. This works well when most points are alive. When 1 point in 100 is alive, about 99 of every 100 candidates it fetches are discarded.
  • Pre-filter. First collect the points alive at \(ts\), then compare \(q\) with each of them. This is exact, and it is the right choice when few points are alive; its cost grows linearly with the number of alive points.
  • Range-filter indexes. These answer queries like “nearest neighbors whose price is between 10 and 20”. They are designed for one number per point, known when the point is indexed; a lifespan is two numbers, one of them unknown at insertion.
  • Timestamp Graph (TG) (Wang et al., ICDE 2025) is, to our knowledge, the one earlier index designed for this problem. TG maintains a single graph, applies the stream one operation at a time, and records for every edge the period during which it existed. A query at \(ts\) reconstructs each visited vertex’s neighbor list as of \(ts\).

TG’s goal is a strong one: the graph it reconstructs for a timestamp is the graph the stream had produced at exactly that operation. That exactness is also what fixes its construction order: operation 1,000,001 can only be applied once operation 1,000,000 is in place, so the build is sequential by design. In our runs of TG’s released code, indexing a million vectors takes between about half an hour and several hours, depending on the dataset and on how long points live (5,749 s for BIGANN at life range 105, the setting of our summary table).

04The tempting fix, and its trap

Parallel ANNS libraries already know how to apply many updates at once, as a batch. So the natural plan is: cut the stream into windows of \(W\) operations, apply each window as one parallel batch, and save an exact snapshot of the graph after each window. A query at \(ts\) uses the most recent snapshot.

Now take a query that lands between two snapshots. Relative to the true state at \(ts\), the snapshot differs in two ways:

  • It may contain points that are not alive at \(ts\). Call these extras.
  • It does not contain points inserted between the snapshot and \(ts\). Call these missing.

The two look symmetric. They are not. Try it on a small example: ten points A to J, twenty operations, windows of five.

An extra is cheap. The search runs into the point, compares two numbers (is \(s \le ts < e\)?), and discards it.

A missing point is invisible. It is not a vertex of the graph being searched, so no beam width will ever reach it. The only remedy is to scan the recent operations separately on every query. A graph search expands a few hundred points, while \(W\) needs to be around 10,000 for batching to pay off, so the scan costs more than the search.

We measured this design as a control. With \(W\) = 104 and about 5,000 points alive, a query lands on average 5,000 operations after its snapshot, half of them insertions: roughly 2,500 of the 5,000 alive points are missing. The measured recall plateaus at 0.57–0.59 for every beam width. With ten times more points alive, the plateau is 0.97–0.98. A variant that uses the nearer of the two surrounding snapshots and scans the operations in between restores recall, and is 1.7–3.2× slower than FlashbackANN at recall 0.95 (1.3–2.2× at recall 0.99).

05Cover-and-filter

FlashbackANN keeps the windows and the batches, and changes one thing: when the graph is frozen. For window number \(c\) it does three things, in this order:

  1. Insert all the points that arrive in window \(c\).
  2. Freeze the graph. This frozen graph is checkpoint \(G_c\).
  3. Delete all the points that expire in window \(c\).

So \(G_c\) contains every insertion up to the end of window \(c\), and the deletions only up to the end of window \(c - 1\). It is deliberately a little too big. Nothing alive during the window can be missing, and whatever is extra gets filtered. Extras now come in two kinds: points that expired earlier in the window, and points that will only be inserted later in it.

Why nothing is ever missing

Take a query at \(ts\) inside window \(c\), and a point alive at \(ts\). Its insertion happened at or before \(ts\), so in window \(c\) or earlier: it was applied before \(G_c\) was frozen. Its expiration happens after \(ts\), so in window \(c\) or later: it was not applied before \(G_c\) was frozen. Therefore the point is in \(G_c\). The query uses checkpoint \(c = \lfloor ts / W \rfloor\) and nothing else.

A few things worth trying in the figure:

  • Short lives are kept. B, F, H and J all live for less than one window. Each is in a checkpoint and is found by queries during its life.
  • A checkpoint is a superset. A expires at operation 5, the first operation of window 1. Since \(G_1\) is frozen before window 1’s deletions, A is in \(G_1\), and the filter removes it every time.
  • Long lives repeat. D is in \(G_0\), \(G_1\) and \(G_2\). Storing that repetition compactly is the subject of section 8.
  • \(W\) is a dial. A larger \(W\) means bigger batches and fewer checkpoints, and more orange bars to filter per query.

What this guarantees, precisely:

  • Coverage: the checkpoint that is searched contains every point alive at \(ts\).
  • Soundness: every point returned is alive at \(ts\).

So the set of eligible points is exact, at the resolution of single operations. The ranking comes from a graph search and is approximate, as in any ANNS index; its quality is what the recall numbers in section 9 measure. And \(G_c\) need not be the graph a one-at-a-time build would have had at any moment: as section 2 ended, any good graph over the right points will do.

06Building it in parallel

Because nothing has to be exact in the middle of a window, each window becomes two big batches with a freeze in between. Inside a batch, the cores of the machine work at the same time. The windows themselves are processed in order, one after another, which is why the window size matters so much.

What happens inside each step:

  • Insert batch. We use the parallel batch insertion of ParlayANN, a library of parallel graph-index algorithms, for the Vamana graph (the proximity graph behind DiskANN). Each new point runs its own beam search over the current graph to find its neighbors, and many points do this at once. Points inserted together do not see each other while searching, so the batch is fed in pieces of doubling size (1, 2, 4, 8, …), which keeps every piece from being much larger than the graph it joins. Edits to the same neighbor list are grouped so that one thread applies them, without locks.
  • Freeze. The current graph is declared checkpoint \(G_c\). From now on it can be read but never changed. Only the newest graph is ever modified; a structure that keeps old versions readable like this is called partially persistent.
  • Delete batch. Expired points are marked dead. From that moment they are logically gone: no later query returns them. Physically they stay in the current graph as stepping stones until enough has accumulated. Once per window the index checks the dead fraction: past 10% it rewires the live vertices around their dead neighbors, and past 50% it rebuilds the current graph from its live points.

The window size \(W\) is the parallelism dial. Larger windows give bigger batches, at the price of more filtering during queries. Our default is \(W\) = 104.

Batching helps even without parallelism, because a whole window is applied at once and recorded as one checkpoint. In our thread-scaling experiment (life range 104), FlashbackANN builds 1.4–17× faster than TG on a single thread and 58–477× faster on all threads.

07Answering a query

A query \((q, ts)\) picks its checkpoint by a division, \(c = \lfloor ts / W \rfloor\), and runs a beam search on \(G_c\). It is the same best-first walk as in section 2. What changes is how \(L\) is counted: there, \(L\) was the size of the candidate list; here it is the number of alive vertices the walk must expand before it stops.

  • If the expanded vertex is alive at \(ts\), it goes into the result pool and counts toward \(L\).
  • If it is not alive, it is not a result and does not count. Its edges are still followed: it acts as a stepping stone.
  • The search stops once it has expanded \(L\) alive vertices, or has nothing left to expand.

The filter runs inside the search. A vertex can be “not alive at \(ts\)” for two reasons, and one comparison handles both: it is one of this window’s extras, or it expired in an earlier window and has not been cleaned out of the graph yet. The extra work in a FlashbackANN query is the time spent on hollow vertices, and it stays small while the alive points outnumber the extras. When very few points are alive, the query takes a shortcut. Two sorted arrays (insertion times and expiration times) give the number of alive points at any \(ts\) with two binary searches. If it is below a threshold (\(W / 10\) by default), the query compares \(q\) with the alive points directly, which is exact and, for so few points, fast. 08Storing thousands of graphs

A stream over a million points has two million operations, which at \(W\) = 104 means 200 checkpoints. A billion points means 200,000. We estimate that storing every checkpoint separately would take about 7 TB at that scale, so cover-and-filter needs checkpoints that are nearly free.

They can be, because consecutive checkpoints are almost identical: a vertex’s neighbor list changes only when a nearby point is inserted or the graph is rewired around a deletion. The question is what unit to share. Here is one vertex whose neighbor list changes twice over five checkpoints:

“Copy every time” and “copy when changed” are per-vertex versioning: the unit is a whole neighbor list. The general-purpose persistent layouts in the library we build on work this way. Replacing a single neighbor stores a new version of the list, and every read first locates the right version.

Our layout is per-edge. Each edge is written down once, with the range of checkpoints [born, died) during which it existed. Space grows with the number of edge changes, not with the number of checkpoints. Each vertex has two parts:

  • a live buffer with the edges that currently exist, in order of birth, and
  • an append-only history: whenever an edge is removed, it is appended with its lifetime, and never touched again.

Appending edges when they die has a useful side effect: the history is sorted by time of death. The history is cut into blocks (32 edges each in the real system, 3 in the figure). A full block is sealed: stored compressed, with a summary of the earliest birth and latest death among its edges, so reading it means decoding it. The newest, not yet full block is the open tail. To read the neighbor list at checkpoint \(c\), a binary search skips every sealed block whose edges had all died by \(c\), and blocks whose edges were all born after \(c\) are skipped by a look at their summary.

TG also records a lifetime for each edge. What is new here is the layout (contiguous, in order of removal, summarized per block, compressed) and that history is recorded once per window. At a billion points it fits in 611 GB (BIGANN) and 853 GB (DEEP) on a machine with 1.5 TB. At 100 million points the most compact of the library’s general-purpose layouts needs 3.0–3.7× the memory of ours, which extrapolates to over 2 TB at a billion.

09Results

All experiments run on one machine with 112 cores (224 hyperthreads, two hardware threads per core) and 1.5 TB of memory, with \(W\) = 104, \(k = 10\) and at most 32 edges per vertex. We use four standard benchmarks of a million vectors each: BIGANN (128-dimensional image descriptors), DEEP (96-dimensional image embeddings), OpenAI (1,536-dimensional text embeddings) and Cohere (768-dimensional text embeddings). Lifespans are synthetic: each point lives for a random number of insertions up to a life range \(R\), so about \(R / 2\) points are alive at once, from about 500 (\(R\) = 103) to about 500,000 (\(R\) = 106). The baselines are TG (run from its authors’ released code, with the same degree limit and construction beam width as ours), pre-filter, post-filter, and a range-filter index adapted to lifespans.

Building the index

Across all four datasets, all life ranges and all six storage layouts we tested (copy every time, three copy-when-changed variants, and two per-edge variants), FlashbackANN on 112 cores builds 41–620× faster than TG. With the same life range on both sides (104), the gap is 1.4–17× on one thread and 58–477× on all threads: the first number is the algorithmic part, and parallelism supplies the rest. At a billion points the build takes 3.2 h (BIGANN) and 3.5 h (DEEP).

At a million points FlashbackANN has 3.3–4.2× the throughput of TG at recall 0.90 and 5.9–34× at recall 0.99 (the largest ratio is on DEEP, where 0.99 is close to the highest recall TG reaches). Across the baselines, FlashbackANN has the highest throughput at nearly every recall level, most clearly at high recall.

  • Recall. Every FlashbackANN layout reaches recall above 0.97 in every setting. TG’s attainable recall decreases as points live longer, down to 0.61 on Cohere at \(R\) = 106.
  • Few alive points. At \(R\) = 103 (about 500 alive), every FlashbackANN query takes the direct comparison from section 7 and returns exact answers 1.2–13.6× faster than TG’s fastest setting.
  • Memory. With the per-edge layout, 0.25–0.50× that of TG at a million points, across all datasets and life ranges.
  • Window size. At \(R\) = 104, growing \(W\) from 103 to 105 speeds up the build 6.6–9.1×. At recall 0.99, \(W\) = 103 answers 1.0–2.7× faster than 104, and 104 answers 3.4–6.2× faster than 105; the per-edge layout’s memory is nearly unchanged. Hence the default of 104.
  • A real update trace. On the creation and deletion times of 10.3 million English Wikipedia pages (13.8 million operations, with BIGANN and DEEP vectors assigned to the pages), FlashbackANN builds in about three minutes against 4.3–5.4 hours for TG (82–120×), and has 8.9–9.8× the throughput at recall 0.95.

Scope. “A billion” is the number of points in the indexed history; at \(R\) = 105, tens of thousands of them are alive at any one moment, at every scale. That is why throughput at a fixed beam width drops by only 1.2–1.6× from 106 to 109 points. Construction is the parallel part; each query runs on one thread, and many queries run side by side.

10Recap

A proximity graph is a navigation aid, so a time-travel index does not have to preserve the exact graph of every past moment. It is enough to have, for every past moment, some graph that contains all the points alive then.

  • Cover. Freezing the graph once per window, after the insertions and before the deletions, gives every query time a checkpoint that contains everything alive.
  • Filter. A two-number lifespan check inside the search removes whatever is extra.
  • Parallel batches. Since nothing has to be exact inside a window, each window is applied as parallel batches: 11.5 s for a million points on 112 cores, and a few hours for a billion.
  • One record per edge. Consecutive checkpoints barely differ, so writing each edge once with its lifetime lets a billion-point history fit in the memory of a single machine.
If you remember one thing

Design the index so that its only errors are the kind a search can filter out. Then build it in batches.
