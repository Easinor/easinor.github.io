01A continent is too big for Dijkstra

Ask a map for the fastest route from Riverside to Boston. Underneath, that is a shortest-path query on a graph: intersections are vertices, road segments are edges, and each edge has a weight, its travel time. The OpenStreetMap road network of North America has 87 million vertices and 113 million edges.

The textbook tool is Dijkstra’s algorithm. It grows a ball around the start, settling vertices (fixing their final distance) in order of distance until it reaches the destination. For a cross-country trip, that ball covers a large part of the continent. In our measurements, one Dijkstra query on North America takes 7.20 seconds on average, and a parallel shortest-path algorithm (Δ-stepping) still takes 0.320 seconds.

The standard answer is to pay once, up front. Contraction hierarchies (CH), introduced by Geisberger et al. in 2008, spend some preprocessing time to build an index: the original graph plus some extra edges. With that index, the same query takes 93.3 microseconds, about 77,000× faster than Dijkstra, and the answer is still exact.

Building that index is the expensive step. This post explains how a CH works (sections 2 and 3), where the build time goes (section 4), and the two ideas in our ICS 2025 paper, SPoCH, that let the build use all the cores of a large machine (sections 5 to 7).

02Contraction: remove a vertex, patch the hole

The idea behind CH is to delete unimportant vertices from the graph one at a time, without ever changing the distance between the vertices that remain.

To contract a vertex v, look at every pair of its neighbors, a and b. If the route a–v–b is a shortest path from a to b, deleting v could make a and b farther apart. So we patch the hole: add a new edge a–b whose weight is the length of that route. This new edge is a shortcut.

If instead there is a strictly shorter way from a to b that avoids v, no shortcut is needed. That other route is called a witness, and the small Dijkstra run that looks for it, stopping as soon as it has reached b, is a witness path search. On a tie we add the shortcut anyway: an extra edge of exactly the right length never changes a distance.

The graph we are working on, meaning the vertices not yet contracted plus the shortcuts added so far, is called the overlay graph. (Real road graphs are directed, because of one-way streets. The pictures here use two-way streets.) Try it:

When every vertex has been contracted, the contraction hierarchy is the original edges, plus all the shortcuts, plus the order in which the vertices were removed. That order is each vertex’s rank: removed later means ranked higher.

The order decides the cost

Any order gives a correct hierarchy. But the two preset orders in the figure end with 2 and 16 shortcuts on the same 13-edge graph, and the best possible order needs just 1. More shortcuts generally mean a bigger index and slower queries.

So builders choose the order with a heuristic score, and always contract a vertex with a low score. The main ingredient is the edge difference: the shortcuts that contracting v would add, minus the edges at v that would go away. The figure shows it in the status line when you select a vertex.

Where the time goesTo know a vertex’s edge difference you must simulate contracting it, which means running its witness searches without changing the graph. And whenever a vertex is contracted, its neighbors’ edge lists change, so their scores must be recomputed. In a sequential builder, scoring, not contracting, is the most time-consuming part.

Real builders, ours included, add a few more terms to the score. The figures in this post use the edge difference alone, except the first map, whose score also counts how many layers of contracted vertices already lie below a vertex, to keep the hierarchy shallow.

03Queries only climb

Why would extra edges make queries faster? Because the hierarchy lets a query ignore almost all of them.

Call an edge upward when it leads from a vertex to a higher-ranked one. A CH query from s to t runs two Dijkstra searches at once: a forward search from s and a backward search from t. Both may only follow upward edges. (On one-way streets the backward search follows edges against their direction; it still only climbs.) Every vertex reached from both sides is a candidate meeting point, and the answer is the best candidate.

This works because every shortest path can be rewritten as one that goes up and then down. Take any shortest path and look at a “valley” on it: a vertex ranked lower than both of its neighbors on the path. That vertex was contracted while both neighbors were still present, and it lay on a shortest path between them, so a shortcut was added across it at that moment, unless an edge at least as short was already there. Replace the valley by that edge and repeat. What remains has a single peak, and both searches reach it.

Why are the two searches small? The intuition: vertices that few routes pass through are contracted early, and the ones contracted last are those that many shortest paths run through, such as junctions of major roads. After a few upward steps a search is on that sparse top layer. You saw this in the first map, where both searches quickly end up on the thick arterials.

Below is the hierarchy of the same ten-vertex graph, drawn with higher-ranked vertices higher up. Several vertices share a level because this hierarchy was built in rounds that remove several vertices at once (section 5). No edge joins two vertices of the same level, so “upward” is still well defined. With only ten vertices the searches cannot be small; the figure is here to show the rule.

An answer path may contain shortcuts. To get real roads back, each shortcut remembers the vertex it bypassed and is unpacked into the two edges it replaced, recursively (standard CH practice; the figure does it in its last status line). Nothing here is approximate: a CH query returns the exact shortest distance.

04Building is the expensive part

On North America, two well-engineered sequential builders take 1341 seconds (the CH builder in KIT’s ULTRA-PHAST code, labeled PHAST below) and 2466 seconds (RoutingKit). A CH is also the starting point of other route-planning techniques, such as transit node routing and hub labeling, so many systems pay this cost, and a long build ties up computing resources and limits how large a graph the method can handle.

In 2009, a year after CH appeared, Vetter observed how many cores can share the work: vertices that share no edge can be contracted at the same time. Almost every parallel CH builder since follows his outline. Work in rounds; in each round, score the vertices, select a set of low-score vertices with no edges among them, and contract the whole set.

We measured two open-source parallel builders on a machine with 96 cores (192 hyperthreads, two hardware threads per core). On North America, OSRM builds the hierarchy in 307 seconds, 4.4× faster than the sequential PHAST build, and CH-Constructor (by Bühler and Nusser) takes 1527 seconds at its best setting, 8 threads. On the three graphs where we recorded their scaling curves (a road network, a chain and a k-nearest-neighbor graph), neither got faster beyond about 16 threads.

Contraction itself parallelizes well. In our analysis, what holds the build back is the work around it.

  • Scoring repeats searches, one whole vertex at a time. After each round, every neighbor of a contracted vertex needs a new score. In both builders each rescoring runs its own witness searches and keeps none of the distances, so two vertices that need a search from the same source both run it. A likely reason OSRM stops scaling is granularity: it handles the affected vertices in parallel, but all the searches of one vertex on one thread. Late in the build only a few vertices with many neighbors remain; if three are left, three threads work and the rest wait.
  • Many threads must edit the same graph. Two vertices contracted in the same round often share a neighbor, and both want to add shortcuts to that neighbor’s edge list at once. CH-Constructor inserts shortcuts through a lock-based structure; in our runs its contraction step stopped improving beyond 16 threads. (Its best total time is at 8 threads for a separate reason: a step that resets its arrays every round grows with the thread count.) OSRM avoids concurrent inserts through its selection rule, which section 7 comes back to.

SPoCH keeps Vetter’s rounds and changes these two things. Section 5 looks at the rounds; sections 6 and 7 are the paper’s contributions.

05Rounds: contract many vertices at once

A set of vertices with no edge between any two of them is called an independent set. Why does a round need one? Suppose two neighbors u and v were contracted together. Contracting u may require a shortcut that ends at v, but v is being deleted at the same moment, so the shortcut would point at a vertex that no longer exists. With an independent set this cannot happen: every shortcut connects two vertices that survive the round.

To pick the set, SPoCH uses Vetter’s local rule with the smallest possible neighborhood: contract every vertex whose score is lower than the scores of all its direct neighbors, breaking ties by vertex label. Two neighbors cannot both be lower than each other, so these local minima form an independent set for free. Each vertex decides by looking only at its own neighbors, so the selection is a parallel loop: a loop whose iterations run on different cores at the same time. (OSRM applies the same rule over two hops.)

The shape in the figure, a fast collapse followed by smaller rounds, is what we observe on real inputs too: usually more than 99% of the vertices are contracted within the first 10 to 20 rounds, and the small core that remains takes many more rounds but little time. These are measurements, not guarantees. On our chain-shaped test graphs, where almost all scores are equal and the tie-breaking decides, a constant fraction of the vertices is still selected in every round.

Inside a round, every step is a parallel loop over many vertices, and a scheduler spreads its iterations over all the cores. The rounds follow one another; the cores share the work within each round.

One detail matters for correctness. Imagine two equally long routes between a and b, one through v and one through v′ (v and v′ are not neighbors, so both can be selected in the same round). If each treated the other as its witness, neither would add a shortcut, and a and b would drift apart. This is why the rule from section 2 adds a shortcut on a tie.

One round of SPoCH has four steps:

  1. LocalSearch. Run the witness searches that the affected vertices need, and store the distances in a shared table. A vertex is affected when a neighbor was contracted in the previous round; in round 1, every vertex is.
  2. Score. Recompute the score of each affected vertex by looking distances up in the table.
  3. Select. Take every vertex whose score is a local minimum.
  4. Contract. Move the selected vertices into the hierarchy and insert their shortcuts, again by table lookup.

Score, Select and Contract follow Vetter’s outline. LocalSearch is new, and it is what turns Score and Contract into lookups.

06Idea 1: search once, look up afterwards

In both parallel builders we compared with, the witness searches run inside scoring and inside contraction: each vertex being scored starts a Dijkstra from each of its neighbors, and each result is used once.

SPoCH moves all of these searches into a step of their own, LocalSearch, and organizes them differently.

  • Batching. Searches are grouped by their source vertex. If three different vertices each need a distance from B, that becomes one Dijkstra from B with three targets, not three Dijkstras.
  • Memoization. Every distance found is written to a shared hash table. A pair that is already in the table is not searched again, in this round or in later ones, until the table fills up and is emptied. This is sound because contraction never changes the distance between two surviving vertices.
  • Pruning. If an edge in the overlay graph is heavier than the distance the table holds for its two ends, the edge is useless and is deleted.

Note what the table stores: the plain shortest distance from a to b in the overlay graph, with nothing excluded. The test from section 2 becomes “is a–v–b exactly as long as that distance?” It gives the same answer, ties included, but no longer mentions v, so one stored distance serves every vertex that asks about the pair.

The figure below replays round 2 of the ten-vertex example, right after round 1 contracted C, E and I. Round 1 scored every vertex, so the table already holds the distance between any two vertices that were two hops apart.

Fewer searches save total work. For parallelism, what changes is the unit of work: one size-capped Dijkstra per source, with all sources running in parallel, in place of all the searches of one vertex on a single thread. Suppose that late in the build three vertices with 500 neighbors each need new scores. One vertex per thread keeps three cores busy; batched by source, the same work is up to 1,500 separate searches that can be spread over every core. Score and Contract are then parallel loops over table lookups.

Like other builders, SPoCH caps the size of each search. If a search stops before reaching a target, the shortcut is added anyway: the hierarchy can end up slightly larger, never wrong, and pruning removes some of these extra shortcuts later.

07Idea 2: a graph that many threads can edit

The overlay graph changes every round: selected vertices leave, shortcuts arrive. But the fastest way to store a graph for reading is a rigid one. In CSR (compressed sparse row) format, all neighbor lists are packed back to back in one big array. Scanning a vertex’s neighbors is a single pass over contiguous memory, but you cannot insert an edge without shifting everything after it.

SPoCH keeps the CSR for reading and puts new shortcuts in a second structure built for writing: a hash table that many threads can insert into at once. Edges are directed, so each one is filed under its source vertex, and a two-way street appears once per direction.

The ten-vertex example after round 1. Crossed-out entries point to contracted vertices and are skipped. The neighbors of B are its CSR segment (A, F) plus whatever the table holds under key B (the new shortcut to D).

The table is phase-concurrent: it is safe as long as all threads are doing the same kind of operation, here inserting. A thread hashes the source vertex to a slot and claims it with a compare-and-swap, an atomic instruction (it cannot be interrupted halfway) that writes only if the slot is still empty. If another thread got there first, it tries the next slot. No thread waits for a lock.

Two contracted vertices can even produce the same shortcut with different weights. Then the entry is updated with an atomic “write the minimum,” so the lighter edge wins whichever thread arrives first.

Whenever the algorithm needs a vertex’s neighbors, it reads the CSR segment and then probes the table. The table is merged into a fresh CSR only when a constant fraction of its slots is full, because late rounds add only a few edges each. Compared with rebuilding the array every round, merging lazily reduces the share of the Contract step from 39.9% to 19.8% of the total running time, on average over our test graphs.

This is also why SPoCH can use the one-hop rule from section 5. OSRM’s two-hop rule means that two vertices contracted in the same round never share a neighbor, so it needs no concurrent structure for inserting shortcuts; the price is smaller sets and, in our measurements, up to 4× more rounds than SPoCH. With safe concurrent inserts, SPoCH can contract vertices that share a neighbor in the same round.

08What we measured

All experiments ran on one machine with 96 cores (192 hyperthreads) and 1.5 TB of memory. We tested 16 graphs: six OpenStreetMap road networks with 3 to 131 million vertices, four synthetic graphs, and six k-nearest-neighbor graphs (each point of a data set linked to its k closest points). We compare with the two parallel builders from section 4, OSRM (by Luxen and Vetter) and CH-Constructor, and with two sequential ones, RoutingKit and the PHAST builder.

An order of magnitude on the large networks. On the four largest road networks SPoCH finishes in 7 to 33 seconds, where the other builders need between one minute and about an hour on the same machine.

The gain comes from scaling. The last row of the table is SPoCH on a single thread. There it is competitive with the sequential builders: behind them on the smallest network, ahead of both on Asia and Europe. With all 192 hyperthreads it runs 28 to 71× faster than on one thread, depending on the graph.

Queries stay close to the best sequential hierarchy. A round-based build contracts many vertices earlier than a sequential build would, so it produces a different hierarchy. To compare hierarchies and not query engines, we took the hierarchy from each builder and ran RoutingKit’s query code on all of them. A query on SPoCH’s hierarchy takes 1.31× as long as on RoutingKit’s on average (1.17 to 1.79× per graph), and queries on the hierarchies from PHAST, OSRM and CH-Constructor take 1.25×, 1.35× and 2.07× as long as on SPoCH’s.

Scope. CH is designed for sparse, road-like graphs, and that is the setting we measured. SPoCH parallelizes the construction; each query runs on one thread, as in any CH.

09Recap

A contraction hierarchy (Geisberger et al., 2008) removes vertices one by one and adds shortcuts so that distances never change; queries then only search upward and finish in microseconds. Building one is dominated by the many small witness searches behind every vertex’s score. Vetter showed in 2009 that an independent set of vertices can be contracted in each round.

SPoCH makes those rounds scale with two changes. LocalSearch runs each round’s witness searches once, batched by source and remembered in a shared table, so that the unit of parallel work is one small search and scoring and contraction become loops of lookups. And the changing graph lives in a compact array plus a hash table with lock-free inserts, merged only occasionally, so threads never wait for each other when they add shortcuts.

On 96 cores (192 hyperthreads) this builds the hierarchy of North America in 23.1 seconds, where the fastest other builder we tested takes 307 seconds, and it is 3.8 to 41× faster than the fastest other builder on each of our 16 graphs, while queries stay close to those on the best sequential hierarchy.

The paper, “Parallel Contraction Hierarchies Can Be Efficient and Scalable” (ICS 2025), has the full algorithms, the data-structure details and the results on all 16 graphs. The code is public.
