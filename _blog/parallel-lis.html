01The problem, and the loop that solves it

Take the sequence 52 31 45 26 61 10 39 44 58 20 70 35. Cross out as few numbers as you can so that what remains goes strictly up. One answer is 10 39 44 58 70: five numbers survive, and no choice keeps six. That is the longest increasing subsequence (LIS) problem: given \(n\) values \(A_1, \dots, A_n\), find the longest subsequence (in order, not necessarily adjacent) that is strictly increasing. Throughout this post \(n\) is the input size and \(k\) is the length of the answer.

Every algorithms course solves it with dynamic programming. Let \(\mathit{dp}[i]\) be the length of the longest increasing subsequence that ends at \(A_i\). An element can extend any subsequence that ends at an earlier, smaller element, so

$$\mathit{dp}[i] \;=\; 1 + \max\Bigl(0,\; \max_{j < i,\; A_j < A_i} \mathit{dp}[j]\Bigr),$$

where the 0 covers an element with nothing smaller before it. The answer is the largest \(\mathit{dp}\) value. The figure below computes it live; the number inside each point is its \(\mathit{dp}\) value.

Evaluated naively the recurrence costs \(O(n^2)\), but one core can do much better. Scan left to right and keep a short list: entry \(r\) is the smallest value seen so far that ends an increasing subsequence of length \(r\). The list is always increasing, so each new element binary-searches for the first entry that is not smaller than it and overwrites that entry (or is appended at the end). The slot it lands in is its \(\mathit{dp}\). On the example the list goes 52, 31, 31 45, 26 45, 26 45 61, and so on. It never has more than \(k\) entries, so the total time is \(O(n \log k)\). This is the tuned sequential baseline in our experiments, called Seq-BS.

So LIS is easy on one core. The interesting question is what happens when you have 96.

02Why more cores do not obviously help

The loop above handles element \(i\) only after elements \(1\) to \(i-1\). That is a chain of \(n\) steps, each waiting for the previous one, and a chain is exactly what extra cores cannot shorten.

Three terms used throughout

Work is the total number of operations an algorithm performs, summed over all cores: what a single core would have to do. Span is the longest chain of operations that must happen one after another: the running time with unlimited cores. With \(P\) cores a good scheduler (the runtime that hands tasks to cores) finishes in roughly work\(/P\) + span. A parallel algorithm is work-efficient if its work matches the best sequential algorithm up to a constant factor.

Is the chain of length \(n\) real? Not quite. The first figure shows what an element actually needs: the \(\mathit{dp}\) values of the earlier, smaller elements, and nothing else. Two elements that do not depend on each other can be computed at the same moment. A chain of true dependences is an increasing subsequence, so the longest one has \(k\) elements, not \(n\).

That suggests processing the input in \(k\) rounds: first everything with \(\mathit{dp} = 1\), then everything with \(\mathit{dp} = 2\), and so on. The two obvious ways to organize those rounds are both expensive:

  • Follow the dependences. Let each finished element notify everyone waiting on it. But there can be \(\Theta(n^2)\) earlier-and-smaller pairs (sorting the first figure produces all of them), so this does quadratic work.
  • Re-check everyone each round. In every round, ask each unfinished element whether it is ready. That is up to \(n\) checks per round for \(k\) rounds: \(\Omega(nk)\) work.

Both are far above the \(O(n \log k)\) that one core needs, and a parallel algorithm that does a hundred times more work needs a hundred cores just to break even. Parallel LIS has a long line of research behind it, and the best earlier algorithms come within logarithmic factors of sequential work. Two reference points, next to the sequential algorithm and ours:

Here \(\tilde{O}\) hides polylogarithmic factors, and “with high probability” means the bound holds except with a vanishingly small chance over the algorithm’s random choices. Krusche and Tiskin’s algorithm is stated in a different model; the bounds shown are its translation to work and span. Their span does not depend on \(k\), and a 2023 result by Cao, Huang and Su also achieves strong worst-case span.

SWGS, our own earlier algorithm, introduced the round-by-round framework this post follows. It finds each round with a two-dimensional search tree and randomization, which costs the extra logarithmic factors in the table and \(O(n \log n)\) space; with 96 cores and \(n\) = 108 it is faster than Seq-BS for \(k\) up to about 100.

What this paper adds is the last row: the same \(k\) rounds, with the same work as the sequential algorithm, in \(O(n)\) space, and with an algorithm of about twenty lines. To our knowledge it is the first parallel LIS algorithm that is work-efficient and has non-trivial parallelism.

03The observation: round one is the prefix minima

Which elements have \(\mathit{dp} = 1\)? Exactly those with nothing smaller before them. Reading left to right, they are the elements that set, or tie, the running minimum. Call such an element a prefix minimum: \(A_i\) is one if \(A_i \le A_j\) for every \(j < i\). (Ties count, because an equal earlier element is not smaller.)

In the example the running minimum goes 52, 31, 31, 26, 26, 10, 10, … and it changes at 52, 31, 26 and 10. Those four have \(\mathit{dp} = 1\).

Now delete them and look again. Take 45: the only smaller element before it was 31, which has just been removed with \(\mathit{dp} = 1\). So 45 can extend it, and its \(\mathit{dp}\) is 2. In general, an element that is a prefix minimum of what remains has had every smaller predecessor removed in round one, so its \(\mathit{dp}\) is at most 2; and it survived round one, so something smaller came before it and its \(\mathit{dp}\) is at least 2. The argument repeats, and gives the lemma the whole algorithm rests on:

Lemma

An element has \(\mathit{dp} = r\) if and only if it is a prefix minimum after all elements with \(\mathit{dp} < r\) have been removed.

So the algorithm is a loop with exactly \(k\) iterations: find all prefix minima, label them with the round number, remove them, repeat. The set removed in round \(r\) is called the \(r\)-th frontier. A frontier goes downhill from left to right, so none of its elements is earlier-and-smaller than another: they do not depend on each other, and a whole frontier can be handled at once.

That counter is why the sweep in the figure is only an illustration. Recomputing a running minimum over the whole remaining sequence costs \(O(n)\) per round and \(O(nk)\) in total, which is the “re-check everyone” strategy again. The real algorithm has to find each frontier while looking only at (roughly) the elements that are in it.

04A tournament tree finds a frontier without scanning

Put the input at the leaves of a complete binary tree and let every internal node store the minimum of the leaves below it. This is a tournament tree (the smaller child “wins” and moves up). It is stored in a plain array, like a heap: the children of node \(i\) are nodes \(2i\) and \(2i+1\). Building it takes \(O(n)\) work.

A round is one recursive walk from the root. The walk carries a single number down the tree, called LMin: the minimum of everything to the left of the current subtree, in the whole array, as it was when the round started.

PrefixMin(i, LMin):
    # LMin = smallest value left of this subtree
    if T[i] == +inf or T[i] > LMin:
        return            # empty, or no prefix minimum inside
    if i is a leaf:
        rank[i] = r       # dp value = round number
        T[i] = +inf       # remove it
    else:
        # read T[2i] before the left child runs
        L = min(LMin, T[2i])
        in parallel:
            PrefixMin(2i,   LMin)
            PrefixMin(2i+1, L)
        # repair the minimum on the way back up
        T[i] = min(T[2i], T[2i+1])

r = 0
while T[1] != +inf:       # one round per dp value
    r = r + 1
    PrefixMin(1, +inf)

Three things are worth noticing.

  • One comparison can dismiss a whole subtree. If the smallest value in a subtree is already larger than something to its left, nothing inside is a prefix minimum, and the walk never enters it.
  • The two children do not wait for each other. The right child needs the minimum of the left child’s subtree, and that number is already stored in the tree. It is read before either child starts (the left child is about to remove elements and change it), so both halves run in parallel and the span of one round is just the depth of the tree: \(O(\log n)\).
  • There is no separate clean-up pass. Removed leaves become \(+\infty\), and each node recomputes its minimum as the recursion returns through it.

The figure runs this on the twelve-number example (padded to 16 leaves with \(+\infty\)). One step is one level of the tree: nodes on a level never wait for each other, so the figure shows them together.

The output is the \(\mathit{dp}\) value of every element, and \(k\) is the number of rounds. Printing an actual longest subsequence takes one more small step, described in the full version of the paper: the predecessor of an element removed in round \(r\) is the last element of round \(r-1\) before it, which is always smaller.

05Why the total work is only O(n log k)

How many nodes does one round touch? Call a node relevant if at least one element of this round’s frontier sits below it. Every node the walk enters is relevant, because the smallest leaf under an entered node is itself a prefix minimum. Every node it tests and skips is a child of a relevant node. So the nodes touched are at most about three times the relevant ones (each relevant node plus its two children), and the relevant nodes are the ones on the paths from the root to the frontier’s leaves.

If the frontier has \(m\) elements, those are \(m\) root-to-leaf paths in a tree with \(n\) leaves. Near the root the paths overlap: with \(n = 16\) and \(m = 4\), the top three levels hold only \(1 + 2 + 4 = 7\) nodes however the four leaves are placed, and below them each path continues alone for the remaining \(\log(16/4) = 2\) levels. In general the shared top has about \(2m\) nodes and each path has \(\log(n/m)\) nodes of its own, so a round with a frontier of size \(m\) costs

$$O\bigl(m \log (n/m)\bigr)$$

work: big frontiers are cheap per element, small frontiers pay up to a full \(\log n\) each. The frontier sizes \(m_1, \dots, m_k\) add up to \(n\), and the sum \(\sum_r m_r \log(n/m_r)\) is largest when all frontiers have the same size. (Try \(n = 16\) in two rounds: sizes 8 and 8 cost \(8 \cdot 1 + 8 \cdot 1 = 16\); sizes 15 and 1 cost about \(1.4 + 4 = 5.4\).) Equal sizes \(n/k\) give \(k \cdot (n/k) \cdot \log k = n \log k\), reading every logarithm as at least 1 so that \(k = 1\) costs \(O(n)\).

Theorem (unweighted LIS)

The LIS of a sequence of length \(n\) with LIS length \(k\) can be computed in \(O(n \log k)\) work, \(O(k \log n)\) span and \(O(n)\) space.

The work matches the sequential algorithm, so the algorithm is work-efficient. The span is \(k\) rounds of depth \(O(\log n)\) each, so it grows linearly with \(k\). The ratio work/span is called the parallelism: it is roughly how many cores the algorithm can keep busy, because beyond that many the span term in work\(/P\) + span takes over. Here it is about \(n \log k / (k \log n)\), which is large whenever the LIS is short compared to the input.

Two notes on reading the figure. The blue curve is a model that counts tree nodes and ignores every constant, and \(n\) here is tiny; on real inputs of 108 to 109 elements the same picture is stretched far to the right (measured results are in section 8). And the inputs are modeled on the two generators used in our experiments: few distinct values for small \(k\), a noisy rising line for large \(k\). \(O(n \log k)\) is a worst case, reached when all frontiers have the same size, as they nearly do in the first kind of input; the second kind has uneven frontiers and costs less, which is why the work curve dips in the middle.

06Weights break the shortcut

In the weighted version every element has a weight \(w_i\), and we want the increasing subsequence with the largest total weight rather than the largest length. The recurrence looks almost the same:

$$\mathit{dp}[i] \;=\; w_i + \max\Bigl(0,\; \max_{j < i,\; A_j < A_i} \mathit{dp}[j]\Bigr).$$

The dependences are unchanged, so the same \(k\) frontiers are still the right schedule. What breaks is the shortcut. In the unweighted problem the value to write in round \(r\) is simply \(r\). Now each element has to compute a real maximum over everything earlier and smaller: among all points below and to the left of mine, which has the best score? We call it a dominant-max query.

The algorithm becomes: compute the frontiers with the tree algorithm; then, round by round, let every element of the frontier ask its dominant-max query in parallel, add its own weight, and store the whole frontier’s scores as one batch. This is safe because elements of one frontier never depend on each other, and everything they do depend on was stored in earlier rounds.

One trick makes these queries simple. Suppose a query only looks at candidates: elements that are already scored and have a smaller value. Then only position and score matter. A candidate is useless if an earlier candidate scores at least as much (the earlier one covers it). Discard the covered ones, and what is left is a staircase: scores go up as positions go right. The best score before position \(q\) is then simply the last staircase point before \(q\).

How does a query get “only the elements with a smaller value”? Sort the elements by value and build a balanced tree over that order, so each tree node stands for a contiguous range of values. Any set of the form “all values below \(x\)” is the union of \(O(\log n)\) such nodes, the same way a binary search visits \(O(\log n)\) nodes. In the example, “smaller than 58” is the node holding the eight smallest values plus the node holding 52. If every node keeps a second structure over its own elements, ordered by position, that can answer “best score before position \(q\)”, a query asks \(O(\log n)\) nodes and takes the best answer.

This two-level structure is a range tree. With an ordinary balanced search tree inside each node, one inner lookup costs \(O(\log n)\), a query costs \(O(\log^2 n)\), and the weighted algorithm takes \(O(n \log^2 n)\) work and \(O(k \log^2 n)\) span. This is the version we implemented and measured.

07Where van Emde Boas trees come in

Can the inner lookup be faster than \(O(\log n)\)? If each node of the range tree stores its elements as a staircase, “best score before position \(q\)” becomes a predecessor query: find the last stored position before \(q\). Positions are integers between 1 and \(n\), whatever the input values are, and for integers there is a classic structure that is faster than a search tree.

A van Emde Boas (vEB) tree stores a set of integers from \(\{0, \dots, U-1\}\) and supports insert, delete and predecessor in \(O(\log \log U)\) time instead of \(O(\log U)\). (It gets there by splitting each key’s bits in half at every level; for this post it is a black box.) With \(U = n\), a dominant-max query drops from \(O(\log^2 n)\) to \(O(\log n \log \log n)\).

The staircase trick for queries was known. The new part is the update: every round inserts a whole frontier into \(O(\log n)\) staircases and deletes the old points that the new ones cover, and to keep the span low all of that has to happen in parallel. To our knowledge there was no parallel vEB tree before, so the second half of the paper builds one:

Theorem (parallel vEB tree)

For a sorted batch \(B\) of keys, batch insertion and batch deletion take \(O(|B| \log \log U)\) work and \(O(\log U \log \log U)\) span. Reporting the \(m\) keys in a range takes \(O((1 + m) \log \log U)\) work and the same span. Single-key operations are unchanged from the sequential vEB tree.

A sorted batch splits into groups that go to independent parts of the tree, which is where the parallelism comes from; batch deletion needs the most care and takes up most of that part of the paper.

Plugged into the weighted algorithm, this gives \(O(n \log n \log \log n)\) work, \(O(k \log^2 n)\) span and \(O(n \log n)\) space (with a space-saving relabeling described in the full version). This is the theoretical result; the measurements in the next section use range trees. Matching the sequential \(O(n \log n)\) bound for weighted LIS in parallel is an open problem.

08How fast is it on a real machine?

We ran the experiments on a machine with 96 cores (192 hyperthreads, two hardware threads per core) on synthetic inputs of 108 and 109 elements, sweeping the LIS length \(k\). The baselines are Seq-BS (the tuned sequential algorithm from section 1), a sequential \(O(n \log n)\) weighted algorithm built on an AVL tree (Seq-AVL), and SWGS (the earlier parallel algorithm). Parallel times use all 96 cores.

The single-core numbers are work-efficiency in practice: the same work as Seq-BS up to a constant, and the measured constant is 1.4–5.5. That is what lets the algorithm overtake Seq-BS with only 8 to 16 cores at \(n\) = 109. Its self-speedup there reaches 25.6× at \(k\) = 102 and 37.0× at \(k\) = 104 on 192 hyperthreads. We believe this is the first parallel LIS implementation that beats the efficient sequential algorithm over a large range of inputs.

Scope. The algorithm targets inputs whose LIS is short relative to \(n\), where the span \(O(k \log n)\) leaves plenty of room for parallelism. For scale, a random sequence has an LIS of length about \(2\sqrt{n}\), which is 2×104 for \(n\) = 108 and about 6×104 for \(n\) = 109; in our tests the parallel algorithm wins for every \(k\) from 1 up to beyond those values.

09Recap

  • The idea. The \(\mathit{dp}\) value of an element is the round in which it becomes a prefix minimum, if you keep removing prefix minima. So LIS takes exactly \(k\) rounds, and everything within a round is independent.
  • Why it is cheap. A tournament tree with one number passed down (the minimum of everything to the left) finds each round’s elements while skipping whole subtrees with single comparisons. The total work is \(O(n \log k)\), the same as the best sequential algorithm, with \(O(k \log n)\) span and \(O(n)\) space.
  • What it achieved. A parallel LIS that is work-efficient in theory and fast in practice: up to 16.8× faster than a tuned sequential implementation on 96 cores, and up to 188× faster than the previous parallel algorithm, in about twenty lines of pseudocode.
  • Beyond LIS. With weights, every element needs a two-dimensional max query each round. Range trees make that practical, and a new parallel van Emde Boas tree, a batch-parallel version of a classic data structure, makes it asymptotically faster.

The paper has the proofs, the full vEB construction and all the experiments, and the code is public (links at the top).
